03 Defects Found

🔴 DEFECT #1: Batch summary "resolved" field is misleading

get_summary() returns "resolved": batch.get("success_count", 0). But success_count is set to total (total records processed), NOT the count of actually resolved exceptions. A batch with 8 exceptions and 0 matched records shows "resolved": 8.

# Batch summary shows:
#   "total_exceptions": 8
#   "resolved": 8          ← This means "8 records processed", not "8 resolved"
#   "unresolved": 0        ← This means "0 failures", not "0 unresolved cases"
#   "auto_resolved": 0     ← Hardcoded
#   "human_review": 0      ← Hardcoded
#   "escalated": 0         ← Hardcoded

# In get_summary():
"resolved": batch.get("success_count", 0),   # Actually = total_records
"unresolved": batch.get("failure_count", 0),  # Actually = 0 (never set to non-zero)

🔴 DEFECT #2: Safety metrics are structurally empty

get_safety_metrics() reads batch fields (auto_decisions, guardrail_blocks, etc.) that are never written by the batch service. All safety metrics return 0. The guardrail_pass_rate returns 1.0 when there are zero decisions — implying 100% pass rate with no data.

# Batch run_batch() stores:
batch["status"] = "COMPLETED"
batch["success_count"] = total
batch["exception_count"] = exceptions
batch["processing_time_ms"] = ...
batch["match_rate"] = ...
batch["matched_records"] = matched

# But NEVER stores:
batch["auto_decisions"]       ← read by get_safety_metrics()
batch["human_decisions"]      ← read by get_safety_metrics()
batch["unresolved_decisions"] ← read by get_safety_metrics()
batch["guardrail_blocks"]     ← read by get_safety_metrics()
batch["high_value_blocks"]    ← read by get_safety_metrics()
batch["conflict_blocks"]      ← read by get_safety_metrics()
batch["novelty_blocks"]       ← read by get_safety_metrics()
batch["verification_failures"]← read by get_safety_metrics()

# Result: safety metrics are always all-zero

⚠️ Root Cause: Batch processing doesn't run the full agent workflow

POST /batches/{id}/run runs only deterministic reconciliation. It does NOT invoke guardrails, verification, decision-making, or resolution execution. Those happen in the LangGraph agent workflow, which is triggered separately. The safety metrics fields are designed for the agent workflow but are queried from the batch registry which never has them.

06 Verdict & Recommendations

✅ What works correctly

GET /metrics, GET /metrics/throughput, and GET /metrics/batches/{id} return real data from the batch registry. The core reconciliation metrics (total_records, matched_records, exceptions, match_rate, timing) are accurate and cross-validated. Nonexistent batch returns 404.

🔴 What needs attention

Defect #1 — "resolved" field in batch summary is misleading. get_summary() maps success_count (total records processed) to "resolved". This should either be renamed to "records_processed" or the field should track actual exception resolution status.

Defect #2 — Safety metrics are structurally empty. The batch service never writes the fields that get_safety_metrics() reads. Either: (a) the batch service should populate safety fields during processing, (b) the metrics should read from a different source (exception statuses), or (c) the endpoint should explicitly indicate "no safety data available" rather than returning misleading zeros.

⚠️ guardrail_pass_rate=1.0 with zero decisions is misleading

When total_decisions = 0, guardrail_pass_rate defaults to 1.0 (100%). This should be null or 0.0 to indicate "no data" rather than "all passed".
