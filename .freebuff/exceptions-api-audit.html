03 Defect: Unrestricted Escalation

🔴 DEFECT: Escalate endpoint lacks state guard

POST /exceptions/{id}/escalate allows escalation from any status (APPROVED, REJECTED, RESOLVED, ESCALATED, PENDING) without checking the current state. In contrast, approve and reject both block non-PENDING/RESOLVED states with a 409 Conflict.

Evidence from Live Server

# Case starts as APPROVED
GET /exceptions/CASE-000001 → status: APPROVED

# Escalate succeeds (should be blocked!)
POST /exceptions/CASE-000001/escalate → 200 OK
  → status changed from APPROVED → ESCALATED

# But approve correctly blocks on ESCALATED
POST /exceptions/CASE-000001/approve → 409 Conflict
  "Cannot approve exception in 'ESCALATED' status"

Comparison with Approve/Reject

EndpointState GuardAllowed StatesBlocked States
POST /approve YES PENDING, RESOLVED APPROVED, REJECTED, ESCALATED → 409
POST /reject YES PENDING, RESOLVED APPROVED, REJECTED, ESCALATED → 409
POST /escalate NO ALL (any status) None — unrestricted

Impact

⚠️ An already-approved exception can be escalated

A reviewer could accidentally escalate a case that was already approved, moving it back to human review and disrupting the workflow. This should either be blocked (like approve/reject) or limited to specific states.

07 Analyze & Explain Fallback Status

⚠️ AnalyzeService main path fails

The POST /exceptions/{id}/analyze endpoint calls AnalyzeService.analyze() which throws an exception. The fallback handler in IntelligenceService._analyze_fallback() constructs a response from the FinancialDataAdapter. This returns real data but with fallback_used=True, llm_provider=none, classification_confidence=None. The analyze endpoint still provides 19 useful fields.

⚠️ LLM unavailable for explanations

The GET /exceptions/{id}/explain endpoint calls ExplainService.explain() which falls back to a deterministic template. This is by design — the system explicitly supports deterministic fallback when LLM is unavailable.

08 Recommended Fix

Fix: Add state guard to escalate_exception route

Add a state check matching the approve/reject pattern. Only allow escalation from PENDING or RESOLVED states.

# In backend/app/api/routes/exceptions.py — escalate_exception()

@router.post("/{exception_id}/escalate")
async def escalate_exception(exception_id: str, request: EscalateRequest):
    svc = get_exception_service()
    exc = svc.get_exception(exception_id)
    if exc is None:
        raise NotFoundException("Exception", exception_id)

    # ADD THIS: state guard matching approve/reject
    if exc.get("status") not in ("RESOLVED", "PENDING"):
        raise ConflictException(
            f"Cannot escalate exception in '{exc.get('status')}' status"
        )

    result = svc.escalate_exception(...)

This is a 5-line change in one file: backend/app/api/routes/exceptions.py.
